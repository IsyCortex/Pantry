# Blocker resolution: Ticket 1.5 migration chain for source-batch relationships

## Ticket

- Ticket 1.5 — Confirm a batch transactionally
- Issue: `#10`

## Original blocker

Ticket 1.5 uncovered a migration-chain defect that prevented reliable verification from a clean database.

### Root cause

1. `migrations/002_create_inventory_items.sql` had been modified after prior application.
2. The file declared `source_batch_id` twice.
3. The file referenced `intake_batches(id)` before `migrations/003_create_intake_batches.sql` created `intake_batches`.

### Impact

- A clean migration run could not progress past migration `002`.
- Passing tests on an existing development database did not prove reproducibility from a fresh database.
- Ticket 1.5 verification was therefore temporarily blocked until the schema evolution path was corrected.

## Resolution

### Repository changes

- Restored `migrations/002_create_inventory_items.sql` to its historical valid scope without `source_batch_id`.
- Added `migrations/004_add_source_batch_to_inventory_items.sql` as the forward corrective migration.

### Why this resolves the blocker

- `002` no longer references tables that do not yet exist.
- `004` adds `source_batch_id` only after `003` creates `intake_batches`.
- Existing environments keep forward schema evolution.
- Fresh environments can apply the migration chain in order.

## Verification evidence

### Clean migration chain

Verified against a fresh database:

1. `001_create_schema_migrations.sql`
2. `002_create_inventory_items.sql`
3. `003_create_intake_batches.sql`
4. `004_add_source_batch_to_inventory_items.sql`

### Test verification

- `npm test` passes after the migration-chain repair.
