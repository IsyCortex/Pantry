# Blocker resolution: Ticket 1.7 bigint identifier type consistency

## Ticket and milestone

- Ticket: `1.7 — M1 release-gate stabilization`
- Issue: `#27`
- Milestone: `M1 — Manual inventory and shared batch workflow`

## Dates

- Encountered: 2026-08-18 (Ticket 1.7 baseline)
- Resolved: 2026-08-18 (commit `9b4f3a90f867037796258d9e09b5aac1c3c57bc5`)

## Original blocker

Ticket 1.7 recorded the M1 release-gate baseline as failing. The recorded failing test was `confirmed items retain their source-batch relationship`, which failed with:

```text
AssertionError [ERR_ASSERTION]: Expected values to be strictly equal: '1' !== 1
```

This prevented the full automated suite from passing from the current `feature/m1` HEAD and blocked release-readiness verification for Ticket 1.5's source-batch relationship acceptance criterion.

## Classification

- Product defect
- Type: application return-path identifier type consistency

## Root cause

The schema and the application return paths disagreed about the runtime type of persisted identifiers:

1. Migrations declared identifiers with integer-backed serial types (`SERIAL`), later normalized to `BIGSERIAL`.
2. PostgreSQL's driver (`node-postgres`) returns `bigint` column values as strings, not numbers.
3. The inventory DB functions returned raw driver rows for `id` and `source_batch_id` without normalizing them to `Number(...)`.
4. Service and test boundaries expected numeric IDs, producing the strict-equality mismatch `'1' !== 1`.

The source-batch relationship itself was present; the failure was a consistency mismatch in the exposed ID representation, not a missing relationship.

## Impact

- The Ticket 1.5 acceptance criterion "Created items retain their source-batch relationship" could not be verified from a clean release baseline.
- Identifier types varied across service boundaries, creating fragility for any consumer comparing or serializing IDs.
- The M1 release gate could not complete while the full suite failed.

## Resolution

### Repository changes

- Normalized migrations to `BIGSERIAL` primary keys (`migrations/001_create_schema_migrations.sql`, `migrations/002_create_inventory_items.sql`).
- Added `Number(...)` coercion for `id` and `source_batch_id` in the inventory DB return paths (`src/db/inventory.js`), while preserving `null` for absent source-batch references.

### Why this resolves the blocker

- Bigint-backed IDs are consistently surfaced as JavaScript numbers across persistence boundaries.
- Service and test expectations now match the actual return types.
- The existing bigint policy for identifiers is now applied consistently across the M1 persistence layer.

## Concurrency safety note (non-blocker clarification)

During Ticket 1.7 verification, additional confirmation-path failures appeared (duplicate inventory rows, `saved === null`, `NOT_FOUND` where `INVALID_STATE_TRANSITION` was expected). These were investigated and classified as **concurrency artifacts**, not an application defect: multiple DB-backed verification/diagnostic processes were run simultaneously against one shared PostgreSQL database, where each process truncates the same tables.

- With a single test process at a time, the full suite passes consistently.
- Release verification must run DB-backed tests as a single process against one database (see Issue `#27`, "Corrected diagnosis and verified serial baseline").
